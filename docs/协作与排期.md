# 协作与排期

北京时间 2026-11-03 至 11-05。角色用于认领工作，不绑定姓名，也不要求六人同时在线。

## 认领方式

每个任务只设一名负责人，可以有协作者。负责人在 Issue 中写明“认领人、预计交付时间、阻塞项”，提交可运行页面、审核内容或可复现记录；不能只报完成百分比。空缺任务优先于加分项。

每日 12:30、21:00 用 10 分钟同步：交付了什么、阻塞是什么、下一次能交付什么。阻塞超过 30 分钟提出，超过 2 小时切换备选路线。

## 少于六人时

| 实际人数 | 组合 | 同时收缩 |
|---|---|---|
| 6 | A / B / C / D / E / F | 完成 P0 后再加第二策略和回放 |
| 5 | A+F / B / C / D / E | A+F 提前完成材料框架，回放由 C 有余力再接 |
| 4 | A+C / B+F / D / E | 只做结果表和事件列表，保留 1 个 benchmark |
| 3 | A+C+F / B+E / D | 8 条知识、1 个配置、10–20 题；周二中午选定最易运行路线，不做回放 |
| 1–2 | A+C+D+F / B+E，或由一人按顺序执行 | 原则上无法保证全部 P0；及时披露缩减范围，不用演示数据代替真实运行 |

A 不必由“最空闲的人”承担，应由能够持续合并和部署的人承担。B+E 合并时先做资源门槛验证，再交替完成内容和评测，避免两条高不确定性工作同时堆到周三。

## 合并约定

- 主分支保持可演示，任务分支使用 `feat/kb`、`feat/qa`、`feat/results`、`eval/baseline`、`docs/content` 等短名。
- 小步 PR，写清用户可见变化、验证方式与未完成项。优先由另一人检查；人数不足时负责人自查并留下记录。
- 同一文件尽量有唯一主责人；修改公共数据结构前先更新技术约定并通知受影响成员。
- 每天至少合并两次。周三冻结时记录部署地址与 commit SHA；关键修复可回退到该版本。
- 不在共享账号、Issue 或代码里放 token。不要提交整份实训目录和原始日志。
