# 评测方案

目标：以可获得的模型资源，完成一个 benchmark 的可追溯小样本实测。先完成一种配置，再争取对比。这里是待执行计划，没有已测成绩。

## 选择路线

| 路线 | 选择理由 | 启动条件 | 停止条件 |
|---|---|---|---|
| 优先：LiveMCPBench 子集 | 与现有 MCP 工具发现、执行和规划调研直接相关 | 模型、工具调用、检索模型/embedding、评审模型、工具环境均可用；具备适合的 Linux/Docker 环境 | 周二累计 2 小时仍无法端到端跑通则转备选 |
| 备选：BFCL 单轮子集 | 先验证函数选择与参数构造，可降低对在线 MCP 环境的依赖 | 存在可用模型调用路径；官方 runner/评分器能用，必要的模型 handler 可接入 | 周二下午仍无生成与评分产物则公开标记“评测未完成” |
| 不作本次承诺 | 多 benchmark 全量跑榜、部署大型企业环境、训练模型 | 不在三天核心范围 | 有余量再另开任务 |

这是基于三天工期与现有资源作出的工程选择，不是 benchmark 学术排名。

[LiveMCPBench 官方 README](https://github.com/icip-cas/LiveMCPBench) 提供 Docker 运行方式，配置涉及生成模型、embedding 与评审；其示例包含 GPU 与 Linux 容器选项，不能直接假设当前 Windows 机器可以无修改运行。是否可去掉 GPU、换检索器或复用已有环境，必须试跑确认；若修改，要记录为实验条件变化。

[BFCL 官方 README](https://github.com/ShishirPatil/gorilla/tree/main/berkeley-function-call-leaderboard) 提供生成与评分流程以及指定任务的运行方式；子集评分不等于官方全量榜单。BFCL 备选测函数调用能力，不能据此声称验证了真实 MCP 协议执行或海量工具检索。

以上官方代码说明在 2026-11-02 查询。正式运行前重新固定 commit 与说明，不能依赖可变的 `main` / `latest` 作为完整复现标识。

## 资源验证

用户目前仅确认拥有 800 美元看山工作台额度。额度金额不等于可调用余额、现金预算或独立 API 授权。

T01 的输出必须覆盖：

| 能力 | 要验证的事实 |
|---|---|
| 外部调用 | 是否有服务端可用 endpoint 和凭证；调用用途是否允许用于网页和脚本 |
| 生成模型 | 实际可选 model ID；文本生成、原生 tool calling 或提示式调用是否可用 |
| 检索 | 是否有 embedding；若没有，评估本地词法检索；改动官方流程需单独说明 |
| 评分 | 是否支持官方要求的 judge；不同 judge 版本的结果不能静默混合 |
| 环境 | Python、Node、uv、Docker/WSL/Linux 的实际可用情况；当前没有已确认 GPU |
| 额度 | 限流、并发、token/金额可见性，以及工作台积分能否抵扣上述调用 |

若额度仅支持桌面产品，继续整理网站与数据结构，同时由团队获得合法可用的 API/执行环境；不能提取隐藏凭证、绕过用途限制，或将桌面对话复制当作自动评测。

## 试跑与扩跑

1. 冻结上游 commit、模型配置与评分版本，先做 3 个不同任务的试跑。确认生成、调用、评分、日志脱敏和导出全链路。
2. 在正式结果产生前冻结目标 20 个任务 ID；保底 10 个。按任务类别分层后以 seed=42 抽样；若资源约束限定可用任务，先固定纳入规则再抽样，保留排除原因。
3. 确认每题的生成、工具与 judge 用量后估算全批成本；设置并发 1–2、请求超时和最大步数。具体值基于试跑填写，不宣称是官方默认。
4. 首次批量消耗建议上限为 50 美元等值额度，但必须先确认计费映射；不可见时以 20 题和步数上限控制。不得自动付费或扩充预算。
5. 第一种配置完成并核对后再跑第二种。可用模型不足时比较同一模型的两种策略；改检索参数等会影响方法，需写入配置，且仍使用相同样本。
6. 结果冻结后导出脱敏文件并人工核对页面；评委只浏览静态产物。

试跑任务可以进入正式集合，但需预先记录它们是用于开发的任务；若依据试跑调整方法，应披露，不能把这部分视作独立未见测试。重复运行次数与不同任务数分别报告。

## 统计口径

对每个冻结任务保留一个正式 attempt；自动重试仅处理瞬时传输错误并记录，不因模型答错反复抽到成功。额外尝试单独展示，不覆盖首个正式结果。

| 计数/指标 | 定义 |
|---|---|
| N | 冻结计划中的不同任务数 |
| S | 正式 attempt 经评分成功的任务数 |
| F | 有效完成评分、但任务不成功的数量 |
| I | 环境或模型 API 故障导致无法完成的数量 |
| J | 已生成但评分器无法判定的数量 |
| U | 计划中尚未执行的数量 |
| 记录完整性 | `N = S + F + I + J + U`，每个任务恰落入一类 |
| 计划成功率 | `S / N`，连同 I、J、U 数量一起显示，作为本项目保守主指标 |
| 已评分成功率 | `S / (S+F)`；分母为 0 时显示无结果，不能显示 0% 或 100% |
| 覆盖率 | `(S+F) / N`，不能只展示已评分成功率隐藏缺失任务 |
| 延迟 | 成功与失败分别记录；说明是模型耗时还是含工具与评分的总耗时 |
| token/费用 | 来自 API 用量；不可得时为 null，不能填估计值或 0 冒充测量 |

页面必须注明上述主指标属于本项目的报告口径；如展示官方 scorer 成绩，使用原名、原始分母单列，不把自定义成功率称为官方分数。不能将 AST 匹配分数解读成真实业务执行成功率。

对比配置需保持任务 ID、评分器、输入、预算和工具环境相同；不可控的实时服务变化与运行时间差要披露。小样本只作探索性观察，展示分子/分母与具体案例。

## 每次运行的产物

```text
experiments/<run_id>/
  config.json          # 上游 SHA、模型、策略、时间、环境、提示与评分版本
  task_ids.json        # 冻结任务 ID、抽样种子与纳入规则
  tasks.json           # 逐题正式结果、状态、评分与运行标识
  summary.json         # N/S/F/I/J/U 与指标
  traces.jsonl         # 脱敏后的可展示事件
  report.md            # 方法、观察、失败分析与限制
  reproduce.md         # 环境、安装、运行、评分和导出的实际命令
```

原始日志保存在本地忽略目录 `private-results/`，审核后只发布脱敏轨迹。数据集如不允许再分发，只保存任务 ID、版本和获取方法。保留参数摘要与可观察动作，不要求记录或公开模型的私有思维过程。

## 结果报告模板

- 本次问题：测什么能力，为什么选该子集。
- 运行范围：模型/策略、N、实际评分类别、环境与上游 commit。
- 指标：S/N、S/(S+F)、覆盖率、失败类型、已记录的成本和耗时。
- 案例：任务 → 实际工具动作 → 输出/目标 → 评分依据 → 失败原因及替代解释。
- 限制：小样本、筛选规则、方法适配、实时依赖与 judge 偏差；不能推广的结论。
- 复现：脱敏配置、命令、逐题记录与来源链接。
