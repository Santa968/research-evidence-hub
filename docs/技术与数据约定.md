# 技术与数据约定

这些约定用于各任务并行开发，尚未实现。开发者可以调整，但须先同步受影响的页面和导出脚本。

## 架构

```text
审核后的 Markdown / JSON ── 构建索引 ── 知识库与站内搜索
                                   └─ 服务端检索 → 模型 API → 引用校验 → 问答页面

独立 Python 评测环境 → 脱敏与统计 → JSON 实验产物 → 结果页与日志回放
```

首版一个 Next.js / TypeScript 应用，静态内容与实验结果从文件读取，问答使用服务端路由。先用词法检索，中文按词或字符 n-gram 处理；经过验收再决定是否增加 embedding。此处网站检索与 benchmark 内部工具检索是两个模块，不能互相混淆。

不引入运行时数据库、队列或在线评测调度。评测依赖与网站隔离，不要求网站服务器运行 Docker。站点托管必须支持 Node 服务端路由和密钥配置；只有静态托管时需独立问答后端，不能将密钥塞进静态页面。

团队本地指南提及 AI Works 等平台，但当前部署能力尚未验证。T02 先验证服务端执行、网络与环境变量，再决定托管平台。

| 路径 | 内容 | 主责 |
|---|---|---|

| `eval/` | 本项目适配、配置模板与导出脚本 | E |

本轮只创建文档和仓库准备文件，上述应用目录由任务负责人在实施时建立。

## 知识条目

元数据至少包含以下字段，正文采用 Markdown；首次实现可以选 JSON sidecar 或 frontmatter，选定后统一。

```json
{
  "id": "tool-discovery",
  "title": "工具发现与工具调用",
  "category": "concept",
  "tags": ["MCP", "工具检索"],
  "updated_at": "2026-11-03",
  "review_status": "draft",
  "sources": [
    {"id": "source-1", "title": "来源标题", "url": "https://example.org/source", "version": null}
  ]
}
```

上述是结构示例，尚非已审核内容。`category` 为 `concept | benchmark | reproduction`；`review_status` 为 `draft | reviewed | disputed`。只有 `reviewed` 条目进入普通问答检索，冲突条目经整理为明确描述分歧的已审核内容后再纳入。

片段 ID 使用稳定的 `条目ID#片段ID`，不依赖运行时数组下标。每个片段保留来源和正文位置，更新内容时同步重建索引。

## 网站接口

| 接口 | 输入 | 输出 |
|---|---|---|
| `GET /api/knowledge` | `q`、`category`、`tag`，均可空 | `{items: [...]}`，只含公开审核后的条目摘要 |
| `GET /api/knowledge/:id` | 条目 ID | 元数据、正文、来源；不存在返回 404 |
| `POST /api/ask` | `{question: string}` | 统一问答响应，见下 |
| `GET /api/runs` | 可选 benchmark/model 筛选 | `{items: [...]}`，每条含来源类型与样本计数 |
| `GET /api/runs/:id` | run ID | 配置、汇总、逐题结果和脱敏事件引用 |

静态页面也可以构建时读文件；接口是共享数据形状约定，不要求为了文件读取重复建立所有路由。

问答成功或资料不足的响应：

```json
{
  "request_id": "request-id",
  "status": "insufficient_evidence",
  "answer": "当前已审核资料不足以回答这个问题。",
  "citations": []
}
```

`status` 为 `answered | insufficient_evidence`。有依据时 `citations` 含 `id`、`title`、`knowledge_id` 或 `run_id`、`anchor`；链接由服务端按已知 ID 构建。模型不得自行决定可跳转 URL。外部来源只允许来自已审核来源表的 http(s) 链接。

错误响应为 `{request_id, error: {code, message}}`。建议 code：`INVALID_INPUT`（400）、`RATE_LIMITED`（429）、`MODEL_UNAVAILABLE`（503）、`UPSTREAM_TIMEOUT`（504）、`INTERNAL_ERROR`（500）。内部堆栈与上游凭证不返回客户端。

首版单次完整响应即可；流式是后续优化。输入最多 2000 字符、每个客户端建议每分钟 5 次请求、服务端生成并发建议 2、请求超时 30 秒；分布式部署时需使用平台限流能力，进程内计数不足以作为跨实例限流。具体配置在接入验证后记录。

检索无片段时不调用生成模型；检索到的资料作为数据传入，不提供执行工具或文件权限。输出存在未知引用、或有事实回答但无有效引用时，返回资料不足/可重试状态，不将其作为通过的回答。

## 实验数据

每个运行配置至少包含：

| 字段 | 含义 |
|---|---|
| `run_id` | 唯一且稳定，建议日期+benchmark+配置+短 SHA |
| `source_type` | `local_run | official_reference | scripted_demo` |
| `benchmark`、`upstream_url`、`upstream_commit` | 基准与固定代码版本 |
| `dataset_version`、`task_ids`、`sampling_seed` | 数据版本、计划样本、抽样种子 |
| `model_id`、`provider`、`endpoint_label` | 模型与提供方；不保存带凭证 URL |
| `strategy`、`prompt_version`、`parameters` | 检索/调用方法、提示、温度、步数等 |
| `scorer`、`judge_model`、`scoring_version` | 原生评分器与实际 judge，未使用为 null |
| `started_at`、`finished_at`、`environment` | 带时区 ISO 时间与系统、依赖锁定信息 |
| `counts` | `planned/succeeded/failed/infra_error/judge_error/not_run` |
| `latency_ms`、`tokens`、`cost` | 实测数据或 null，注明货币/单位与计量范围 |
| `limitations`、`artifact_paths` | 限制和公开产物位置 |

逐题记录包含 `task_id`、`attempt_id`、`status`、`score`、`scoring_evidence`、`error_type`、`duration_ms` 与 `trace_path`。状态取 `succeeded | failed | infra_error | judge_error | not_run`，与评测方案的计数一一对应。重试另存 `attempt_id`，正式汇总明确选用的 attempt。

`official_reference` 保留其原始指标名和原分母，不强塞进本项目计数；`scripted_demo` 从全部实验统计中排除。三种来源在页面上始终可辨。

回放事件至少有 `event_id`、`sequence`、`task_id`、`timestamp`、`type`、`tool_name`、`arguments_summary`、`result_summary`、`duration_ms`、`status`。事件类型建议 `retrieve | tool_call | tool_result | final_answer | error`。可观察动作可记录，私有推理不作为采集要求。

## 配置与发布

`.env.example` 只放变量名与空值。实际 provider 确认后更新变量映射，不假定 OpenAI 兼容。密钥不用 `NEXT_PUBLIC_` 前缀，不写进图片、录屏、日志或样例 JSON。

部署前完成构建与主流程验收，发布包包含静态索引、审核内容和结果。若模型服务异常，页面明确提示并保留知识库与已完成实验；标注的离线演示不触发付费调用，也不伪装成实时答案。
